# v0.2 frame-sampling benchmark results

Issue [#22](https://github.com/mayank-gupta16/vision-query-system/issues/22)
selects fixed nearest-PTS 5 FPS as the v0.2 evaluation default. Fixed 5 FPS is
the lowest-sample policy that passes every frozen event-recall,
missed-track-opportunity, failure, real-time, and memory gate. This is a
ratified input to later adapter design, not a change to the existing public
sampler or approval to ship the detector runtime.

## Decision

Fixed 1 FPS misses every cut-adjacent event and recalls only 70.83% of events
overall. Fixed 2 FPS recalls every event once, but 29.16% of events have fewer
than two matched observations; every cut-adjacent event is a missed-track
opportunity. Fixed 3 FPS also recalls every event, but one of six small/fast
events has only one matched observation, exceeding that stratum's 10% ceiling.

Fixed 5 FPS, fixed 8 FPS, and adaptive 3-to-8 FPS all produce 100% event recall,
zero missed-track opportunities, and zero failures. Fixed 5 FPS wins the
preregistered cost rule at 300 samples per source minute. Adaptive consumes 455
samples/minute and fixed 8 consumes 470, respectively 51.7% and 56.7% more than
fixed 5, without improving a gate metric.

The adaptive calibration selects motion threshold `0.03`. All four thresholds
pass with identical accuracy and 181 samples across four six-second clips, so
the declared sample-count/lower-threshold tie-break chooses `0.03`. On test,
that threshold activates on 69–70 of 86 frames per clip and therefore behaves
nearly like fixed 8 FPS. It is not selected as an automatic override.

## Measured accuracy

Values are median test-set percentages across five isolated repetitions.
`Recall O/S/C` is overall / small-fast / cut-adjacent event recall. `Missed
O/S/C` is the corresponding missed-track-opportunity rate. Camera-motion and
VFR-gap recall are 100% for every policy; their missed-opportunity rates are 0%
except at fixed 1 FPS, where both are 100%.

| Policy | Gate | Recall O/S/C | Missed O/S/C |
| --- | --- | --- | --- |
| Fixed 1 FPS | **Fail** | 70.83 / 83.33 / 0 | 100 / 100 / 100 |
| Fixed 2 FPS | **Fail** | 100 / 100 / 100 | 29.16 / 16.66 / 100 |
| Fixed 3 FPS | **Fail** | 100 / 100 / 100 | 4.16 / 16.66 / 0 |
| Fixed 5 FPS | **Pass** | 100 / 100 / 100 | 0 / 0 / 0 |
| Fixed 8 FPS | **Pass** | 100 / 100 / 100 | 0 / 0 / 0 |

Every accuracy and sample-rate median has zero median absolute deviation. The
failed policies are retained as research results; their receipts are not
waived.

## Measured resources and timing

The six test clips represent 36 source seconds. RTF is source duration divided
by end-to-end sampling/detection wall time; its parenthesized value is median
absolute deviation. Detector wall and CPU are median seconds per complete test
repetition. Logical storage is packed sampled RGB24 only. Peak process RSS is
the worst observed 545.89 MiB for every candidate because the parent retains
the complete result set and therefore carries the run's earlier high-water
mark.

| Policy | Samples/min | RGB MiB/min | RTF (MAD) | Detect wall / CPU | Median / max nearest-PTS error |
| --- | ---: | ---: | ---: | ---: | ---: |
| Fixed 1 FPS | 60 | 14.24 | 16.026x (0.807) | 1.703 / 1.561 s | 0 / 0 ms |
| Fixed 2 FPS | 120 | 28.48 | 10.833x (0.184) | 2.716 / 3.452 s | 33 / 33 ms |
| Fixed 3 FPS | 180 | 42.71 | 9.248x (0.317) | 3.316 / 4.604 s | 1 / 1 ms |

The 5-FPS maximum nearest-frame error occurs at the intentional enlarged VFR
frame duration; it is reported independently and never replaces source PTS.
Its median decode/sample wall time is 0.551 seconds per repetition. Adaptive's
tile scan raises that phase to 2.269 seconds while saving only nine frames over
fixed 8 across the six clips.

## Default and override triggers

The ratified v0.2 input is:

- use fixed nearest-PTS 5 FPS by default;
- do not enable the measured tile-difference adaptive policy automatically;
- do not raise the rate merely for camera motion, a cut, or a source-frame gap
  up to the tested 333 ms frame duration—fixed 5 passed those strata;
- expose a bounded fixed 8 FPS expert override when the caller requires more
  than two matched observations per event, expects relevant events shorter than
  the tested 880 ms minimum, or encounters source-frame durations above 333 ms;
- revisit 5 versus 8 FPS if issue #24's tracking gate fails at 5 FPS and passes
  at 8 FPS. That downstream measured failure is the only automatic product
  escalation trigger currently justified.

The three boundary triggers identify conditions outside this experiment; 8 FPS
is the conservative measured upper candidate, not a claim that it solves
unmeasured content. Shorter events or larger PTS gaps should remain explicitly
unsupported/uncertain until separately validated.

## Calibration correction

The first locked fixture used a 104-pixel small/fast target. Its calibration
stopped before test because one source had zero detections even on the
high-rate schedule, so the fixture measured a detector ceiling rather than
sampling loss. The issue log and
[methodology](v0.2-sampling-methodology.md) preserve the amendment: 128 and 136
pixels still failed; 144 pixels was the first tested 8-pixel step with at least
two detections for every calibration event. The dataset was fully regenerated
and relocked before any test inference. No test result exists for the invalid
104-pixel fixture.

## Limits and next boundary

The result covers six short test clips, one vehicle class, synthetic motion,
one detector/threshold, and one CPU profile. The generated scenes are less
complex than real traffic and do not cover compression artifacts, dense
objects, pedestrians, bicycles, weather, real camera cuts, sub-880-ms events,
or frame durations above 333 ms. The adaptive score is deliberately simple and
did not discriminate the measured motion regimes. These results do not establish
tracking quality; issue #24 must test whether two or more detections become a
stable short-term tracklet.

No model, runtime, source image, generated frame, clip, or wheel is added to the
release. Product integration still requires a sampler configuration boundary,
the Detector/Tracker contracts and adapters, dependency/weight distribution
review, and v0.2 regression receipts.
